# Approved Tools and HIPAA Safety

<p class="module-lede">A tool can be approved for one purpose without being approved for every account, information type, or workflow. Safe use begins with permission, not with the prompt.</p>

## Module Overview

This module explains how to choose an approved AI tool and determine whether a specific account, information type, task, sharing method, and destination are permitted. It is important because a tool can be approved for one purpose while remaining unsuitable for another.

::: warning DWIHN confirmation required
Replace generic examples in this module with DWIHN's current approved-tool catalog, HIPAA/privacy guidance, account requirements, and help route before delivery.
:::

## Learning objectives

By the end of this module, learners can:

- Explain why "approved tool" does not mean "approved for everything."
- Check the tool, account, information, task, sharing, and destination.
- Pause and use the designated help route when permission is unclear.
- Apply the same protection to AI outputs that applies to their content.

### 1. The DWIHN approved tool catalog

**Detailed Explanation:** The approved tool catalog should tell employees which tools and features may be used, which organizational account is required, who may use them, which tasks are allowed, and what information is prohibited. Approval applies to a defined workflow, not automatically to every feature carrying the same product name.

**Key Points:**

- Confirm the exact tool, feature, account, role, data, and task.
- Product-name approval does not approve every configuration or feature.
- The current DWIHN catalog is the controlling course reference.

::: tip Real-life example
An employee is allowed to use an organizational writing assistant for a public training announcement. That approval does not automatically permit the employee to enter a member letter or call transcript into the same tool.
:::

**Technical Example:** A catalog can be represented as a permission matrix with fields for tool, feature, permitted roles, allowed data classes, approved tasks, output destination, and support owner.

**How It Works:**

1. Identify the task and intended result.
2. Locate the exact tool and feature in the catalog.
3. Confirm the required organizational account and learner role.
4. Check permitted data and output destinations.
5. Proceed only when every condition matches; otherwise use the help route.

**Where It Is Used:** Selecting generative AI tools, Lumenore features, Genesys functions, Teams capabilities, export options, and any new AI-supported workflow.

**Common Mistakes or Confusions:**

- Assuming a familiar product name means the whole product is approved.
- Using a personal account for an organizational task.
- Relying on an old screenshot or memory instead of the current catalog.

### 2. HIPAA and privacy boundaries

**Detailed Explanation:** Before entering information, the employee must check whether the tool, account, configuration, data type, and task are specifically permitted. The employee should use only the minimum information necessary for the authorized purpose and follow DWIHN's confirmed privacy guidance.

**Key Points:**

- Tool approval alone does not authorize every kind of health information.
- Use the minimum information required for the approved purpose.
- Inputs, outputs, exports, recordings, and sharing all require attention.

::: tip Real-life example
A staff member wants help improving a fictional service letter. The safe training exercise uses invented names and facts. A real letter would require the exact approved production workflow and privacy review.
:::

**Technical Example:** An approved application may use access controls, encryption, audit records, retention settings, and configured data boundaries. These controls support privacy, but employees must still follow the authorized workflow.

**How It Works:**

1. Identify the information involved.
2. Check its classification and whether it may enter the selected tool.
3. Confirm the account, access, sharing, and retention configuration.
4. Reduce the input to what the task requires.
5. Review and handle the output under the same applicable protections.

**Where It Is Used:** Member communication, case-related summaries, call transcripts, meeting recordings, analytics, exports, and any workflow involving health or identifying information.

**Common Mistakes or Confusions:**

- Treating an approved tool as blanket permission.
- Assuming removal of a name always makes information safe.
- Protecting the input but sharing the generated output too broadly.

### 3. Data sensitivity affects tool choice

**Detailed Explanation:** Public, internal, confidential, and restricted information require different handling. A tool suitable for public content may not be suitable for internal reports or identifiable health information. Module 3 provides the detailed classification practice.

**Key Points:**

- Classify before selecting the tool or feature.
- Combined details may be more sensitive than each detail alone.
- Use DWIHN's exact tier definitions and handling rules.

::: tip Real-life example
A published service description may be appropriate for an approved public-writing task. A screenshot containing a case number and service note requires a different classification and permission decision.
:::

**Technical Example:** A document-management system may store a classification label in file metadata and use it to limit sharing, downloading, or access. The label is useful only when the content was classified correctly.

**How It Works:**

1. Inspect the complete information, including hidden or combined details.
2. Assign the applicable DWIHN tier.
3. Read the handling rule for that tier.
4. Match the rule with an approved tool and destination.
5. Pause when the classification or permission is uncertain.

**Where It Is Used:** Email, documents, dashboards, screenshots, transcripts, exports, presentations, recordings, and prompt inputs.

**Common Mistakes or Confusions:**

- Classifying only by filename or storage location.
- Looking only for names and ignoring other identifiers.
- Assuming internal information may be entered into any internal tool.

### 4. What to do when a rule may have been broken

**Detailed Explanation:** Employees should stop unnecessary activity, avoid independent cleanup, record known facts, and follow DWIHN's confirmed help or reporting process. Prompt reporting allows authorized teams to assess the issue and provide instructions.

**Key Points:**

- Report uncertainty early; do not wait to prove that an incident occurred.
- Record known facts without guessing or assigning blame.
- Follow authorized instructions instead of deleting evidence independently.

::: tip Real-life example
After submitting a prompt, an employee realizes the wrong organizational account may have been used. The employee does not delete evidence or continue the task; they follow the confirmed DWIHN reporting route.
:::

**Technical Example:** Useful technical facts may include the tool, feature, account, approximate time, information type, prompt or action performed, output destination, and any visible error message.

**How It Works:**

1. Recognize the possible rule violation.
2. Stop unnecessary additional activity.
3. Take only the immediate protective action authorized by policy.
4. Report through the confirmed DWIHN route.
5. Preserve facts and follow responder instructions.

**Where It Is Used:** Wrong-account use, unauthorized uploads, inappropriate exports, accidental sharing, misleading outputs, and any uncertain AI workflow.

**Common Mistakes or Confusions:**

- Hiding an error or delaying the report.
- Deleting a conversation or file without instruction.
- Contacting affected people or investigating beyond the employee's role.

## Six permission checks

<div class="workflow">
  <div class="workflow-step"><b>Tool</b><span>Is this application approved for organizational use?</span></div>
  <div class="workflow-step"><b>Account</b><span>Am I using the required organizational account?</span></div>
  <div class="workflow-step"><b>Information</b><span>Is this type of data permitted in this tool?</span></div>
  <div class="workflow-step"><b>Task</b><span>Is this specific use authorized?</span></div>
  <div class="workflow-step"><b>Sharing</b><span>Who can access the input and output?</span></div>
  <div class="workflow-step"><b>Destination</b><span>May the result be stored or sent there?</span></div>
</div>

All six checks must support the action. If one answer is unknown, pause and ask through the approved route.

## Story: approved tool, wrong information

Sam uses an organizational writing assistant that is approved for public communication. Sam wants to improve a letter and considers pasting member-specific information into the tool.

The tool's approval for public writing does not prove that member information is permitted. Sam must check the approved use, account configuration, data rules, and review process before entering anything.

## Tool familiarity without overpromising

Use DWIHN's verified catalog to explain the purpose and boundary of each available tool. A useful catalog entry answers:

- What the tool is approved to do.
- Which organizational account or environment is required.
- Which roles may use it.
- Which data types are allowed or prohibited.
- Where outputs may be stored or shared.
- Who answers questions and approves exceptions.

## Safe output handling

An AI output can repeat or transform sensitive information. A summary, translation, chart, or exported report may require the same or stronger handling as its source.

## Common mistakes

- Using a personal account because it is convenient.
- Treating brand name approval as approval of every feature.
- Entering information before checking its classification.
- Assuming an output is less sensitive than its source.
- Sharing a result through an unauthorized location.
- Continuing when the policy is unclear instead of asking.

## Ethical consideration

People receiving behavioral-health services may have little visibility into how workplace technologies are used. Employees should use only authorized workflows, limit information to what the task requires, and preserve human accountability.
